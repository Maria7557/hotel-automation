Both request lists use `GET /v1/dashboard`. The endpoint accepts `status` (`all`, `new`, `waiting`, `payment`, `completed`, `attention`), `search`, `sort` (`asc` or `desc` by time received), `page` (starting at 1), and `limit` (1–30, default 30). The app requests 30 offers per page. Changing filters, search or sort returns to the first page.

Filtering, search, sorting and pagination happen in PostgreSQL. Requests with identical timestamps are ordered by ID. The response includes `pagination: { page, limit, total }`, where `total` is the full filtered count, and dashboard `counts` for all of today's requests in the hotel's timezone. Counts and page data use one read-only transaction with a consistent snapshot. Pages beyond the last page are clamped to the last available page, including after marking payment links sent. The app displays the number on the current page as “30 out of N”, with Previous/Next controls and the page number.

Every unfinished request shows the same live clock pill: new, error/review-needed, payment-link-needed and waiting-for-reply. `offerSentAt` is the earliest successful delivery time for the latest offer; older offer versions and queued/failed deliveries do not start the reply timer. Payment-link waiting uses `acceptedAt`. New and error/review-needed cards count from `receivedAt`; payment and reply cards also fall back to `receivedAt` when their workflow timestamp is missing or invalid. All timers update every minute and when the app returns to the foreground. Completed requests have no action timer. The To do list includes New requests, payment links and errors, and its count includes all three groups.

The Not delivered counter uses `counts.needsAttention`, matching the full `attention` request list across pages. It includes delivery failures, automatic sending timeouts and requests needing review. There is no separate failed-delivery subtotal. Connection warnings appear separately and do not increase request counts. Demo counts are calculated from the current requests.

New request cards keep a neutral background and text, using orange only for status indicators. They show the current sending stage for each channel: Queued, Processing, Waiting for connection, or Awaiting automatic retry. `channelDetails` includes the raw delivery `state`, `attemptCount`, and `lastErrorCode`, so waiting for a connection is distinguished from a provider retry. Failed, uncertain, or cancelled deliveries retain explicit labels instead of being presented as queued. These details appear on collapsed cards and the reservation page. New request tooltips explain that automatic processing is expected, while error/review tooltips call for hotel action. Missing or inconsistent delivery data is explained explicitly without promising automatic sending.

A request still waiting for its first successful offer delivery moves from New to errors at 15 minutes, with `attentionReason: "automatic_sending_timeout"`. The window starts when the current offer version is created, or when the request arrives if no offer exists. Delivery retries and connection deferrals do not restart the window; a new offer version does. Dashboard SQL filtering, counts, reservation details, and demo mode use the same limit. `processingDeadlineAt` identifies a reservation's deadline, and `nextProcessingDeadlineAt` is the earliest pending deadline across the whole dashboard, allowing open lists and reservation pages to refresh automatically. An accepted offer or completed request keeps its existing status. A successful delivery clears the derived timeout; the error does not cancel a queued retry or an in-progress send.
