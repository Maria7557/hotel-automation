# Архитектурные решения MVP

## ADR-001 — Expo Native для сотрудников

Приложение владельца и менеджера создаётся на Expo/React Native из одной кодовой базы для iOS и Android. Публичная форма и предложение остаются веб-страницами, поскольку гостю не нужно устанавливать приложение.

## ADR-002 — модульный монолит

API, публичные страницы, интеграционные callbacks и worker находятся в одном TypeScript-приложении. Границы модулей сохраняются в коде, но отдельные сетевые сервисы не создаются. Это уменьшает эксплуатационную стоимость и не мешает позднее вынести доказанно нагруженный модуль.

## ADR-003 — PostgreSQL как источник истины и очередь MVP

Рабочие данные и задания доставки хранятся в PostgreSQL. Worker забирает задания с блокировкой записи, сохраняет попытки и может продолжить после перезапуска. Redis и внешний message broker не нужны до появления измеренной нагрузки.

## ADR-004 — факты вместо длинной статусной машины

Заявка хранит факты: создана, предложение выпущено, принято, истекло, отозвано или закрыто. Видимый статус, предупреждение и следующее действие возвращает одна чистая функция доменного пакета. Ошибка канала не становится статусом заявки.

## ADR-005 — неизменяемая версия предложения

Каждая отправленная версия содержит снимок бренда, номера, фотографий, условий и построчного расчёта. Последующее изменение тарифа или шаблона не переписывает уже отправленное предложение и согласие гостя.

## ADR-006 — интеграции через адаптер Delivery

Google email, WAHA, Expo push, тестовые сообщения и локальные заглушки используют одну модель доставки. Доменная логика не зависит от API конкретного провайдера. Секреты доступны только серверу.

## ADR-007 — включительная дата в UI, полуоткрытый диапазон в расчёте

Пользователь вводит понятные даты «от» и «до» включительно. API преобразует окончание в `endExclusive`, а расчёт работает с `[start, endExclusive)`. Для одной комнаты и одного тарифного плана пересечения запрещены.
