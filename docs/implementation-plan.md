# Hotel MVP — план реализации

Версия 1.0 · 31 октября 2026

## Результат MVP

Владелец отеля создаёт аккаунт в Expo-приложении, заполняет профиль, добавляет категории номеров и тарифы по датам, подключает Google-почту и WhatsApp через WAHA, настраивает сообщения и отправляет тесты. Заявка с embed-формы автоматически превращается в рассчитанное предложение. Гость получает ссылку, открывает брендированную веб-страницу и нажимает Accept. Владелец видит в dashboard, что требуется проверить наличие.

Оплата, PMS, автоматическое подтверждение наличия, конструктор процессов и приглашение сотрудников через UI не входят в первый релиз.

## Архитектурные правила

- Expo + React Native + TypeScript для iOS и Android.
- Один TypeScript-сервер обслуживает API, embed-форму, страницу предложения, webhooks и фоновые задания.
- Одна PostgreSQL-база. Redis, брокер сообщений и микросервисы не используются.
- Фоновый обработчик запускается из той же кодовой базы и хранит задания в БД.
- Шесть основных бизнес-сущностей: Hotel, Room, RatePeriod, Inquiry, OfferVersion, Delivery.
- Факты хранятся в данных; видимый статус и следующее действие вычисляются одной общей функцией.
- Предложение является неизменяемым снимком. Из него строятся email, WhatsApp, веб-страница и экран принятого предложения.
- Delivery используется для тестовой и реальной отправки email, WhatsApp и push.
- Все интерфейсы следуют `docs/brand-book.md` и токенам из `design/tokens.json`.

## Тарифная модель MVP

Для каждой категории номера и тарифного плана задаются:

- дата начала и включительная дата окончания;
- цена за номер за ночь в центах;
- валюта;
- room-only или breakfast;
- включённые взрослые и дети;
- доплата за дополнительного взрослого или ребёнка;
- максимальный возраст ребёнка;
- минимальное число ночей.

В расчёте используется полуоткрытый диапазон `[start, endExclusive)`. Пересечения периодов одной комнаты и одного плана запрещены. Если хотя бы одна ночь не покрыта тарифом, автоматическое предложение не отправляется.

## Задачи

### V0 — рабочая основа

- npm workspaces: `apps/mobile`, `apps/server`, `packages/domain`, `packages/contracts`, `packages/design`.
- Expo-приложение, сервер, общие контракты и токены.
- TypeScript, unit tests и единая команда `npm run check`.
- Health API и локальная конфигурация без секретов в клиенте.

Критерий: зависимости устанавливаются, typecheck и tests проходят, приложение и API запускаются отдельными командами.

### V1 — аккаунт и профиль отеля

- Регистрация и вход владельца.
- Создание профиля: название, описание, EUR, Europe/Rome, контакты, логотип, фотографии и условия.
- Onboarding и сохранение сессии.
- Архитектурная готовность к `hotel_members`, без UI приглашений.

Критерий: новый пользователь проходит onboarding с чистой установки и видит сохранённый отель после повторного входа.

### V2 — номера и тарифы

- CRUD категорий номеров.
- Вместимость, кровати, удобства, питание, фотографии.
- CRUD тарифных периодов и запрет пересечений.
- Построчный расчёт по ночам, взрослым и детям.
- Контрольные тесты границ периодов и отсутствующего тарифа.

Критерий: контрольные проживания рассчитываются точно, а пробел тарифа блокирует автоотправку.

### V3 — форма, заявка и предложение

- Изолированная embed-форма и публичный intake API.
- Idempotency, server-side validation, honeypot и allowlist доменов.
- Автоподбор подходящих категорий и создание OfferVersion.
- Fake-адаптеры для локальной разработки и общий Delivery worker для реальных каналов.
- Экран заявок и вычисляемое следующее действие.

Критерий: повтор одного payload создаёт одну заявку, одну версию предложения и нужные доставки.

Статус: выполнено. Без credentials test-send остаётся явно обозначенным fake; с подключённым каналом worker использует реальный провайдер.

### V4 — веб-предложение и Accept

- Брендированная SSR-страница с active/accepted/expired/revoked.
- Публичный случайный токен; в базе хранится только hash.
- Accept через идемпотентный POST, не через GET.
- Состояние точной принятой версии и следующее действие в dashboard.

Критерий: полный локальный путь заканчивается состоянием «Требуется подтверждение наличия» в приложении.

Статус: выполнено для MVP. Push и отдельный экран деталей принятой версии перенесены в пилотный этап.

### V5 — шаблоны и Google

- Редактор email/WhatsApp с ограниченными переменными.
- Preview и тестовая отправка используют тот же renderer и Delivery.
- Gmail OAuth с минимальным scope отправки.
- Контролируемые повторы и понятное состояние отозванного доступа.

Статус: реализовано. Для реальной проверки требуются OAuth credentials и разрешённый redirect URI.

### V6 — WAHA

- Настройка session, проверка состояния подключения и диагностируемые ошибки.
- Тестовая и реальная отправка через общий Delivery.
- Консервативная обработка timeout, rate-limit и неоднозначных сетевых ошибок.
- В UI явно обозначается неофициальный характер подключения.

Статус: реализовано. Для реальной проверки требуются доступный WAHA server, session и тестовый WhatsApp-номер.

### V7 — пилотная готовность

- Показатели: новые заявки, приняли предложение, требуют внимания.
- Фильтры используют ту же функцию состояния, что и карточки.
- Rate limit, безопасная загрузка изображений, логи без PII, backup и monitoring worker.
- Unit, integration, web E2E, mobile smoke, Android и iOS release builds.

## Внешние данные, не блокирующие локальную разработку

- Google OAuth credentials.
- Тестовый номер и работающая WAHA-сессия.
- Домен и production PostgreSQL/Storage.
- Apple и Google developer accounts.
- Финальные название, логотип, фотографии, privacy и consent-тексты.

До их получения test-send работает через явно обозначенный fake-результат; production worker отправляет только через реально подключённый канал.
